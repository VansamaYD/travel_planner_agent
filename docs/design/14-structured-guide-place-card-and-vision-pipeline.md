# 结构化攻略、地点知识卡与按需视觉流水线

> 状态：1.0-implementation-baseline  
> 日期：2026-09-01  
> 目标：把聊天中的外部资料转成可选择、可追踪、可复用和可持续修订的旅行知识。

## 1. 核心决策

系统不把攻略或地点事实只保存在模型回答中，而采用三层结构：

1. `GuideCandidate`：搜索发现的轻量候选，只含来源标识、标题、作者、摘要和访问令牌；
2. `GuideLibraryItem`：用户明确选择后下载的原文快照，保存正文、图片引用、部分评论、互动摘要、用户编辑和采集时间；
3. `PlaceKnowledgeCard`：从地图、攻略、视觉识别和用户修订中持续合并的地点实体，可表示景点、餐厅、酒店、车站、机场或其他地点。

模型的聊天文本是展示层，不是事实源。地图坐标、营业时间、预约要求、价格和推荐项目等均应引用结构化卡片及其来源时间。

## 2. 攻略状态机

```text
discovered -> downloading -> ready
                    |          |
                    v          v
                  failed <- refresh
```

- 搜索结果先以 `discovered` 加密落库，并通过消息附件显示为可勾选卡片；
- 用户点击保存后，系统按选择顺序调用只读 `get_feed_detail`；
- 下载阶段保存进度，成功后进入 `ready`，失败保留候选并允许重试；
- 同一用户、Provider 和外部内容 ID 只有一个记录，重新搜索或刷新只更新版本；
- 攻略删除只删除本地副本，不操作来源平台。

小红书 Worker 只允许 `search_feeds` 与 `get_feed_detail`，主系统不映射发布、点赞、收藏或评论工具。详情默认只获取首批评论，避免无边界滚动与风控风险。评论提取同时兼容直接数组与 `comments.list/items/commentList` 等嵌套结构；用户可单独点击“刷新评论”以 `load_all_comments=true` 绕过详情缓存。若来源 Worker 本身未返回评论，界面保留原数据，不伪造内容。

详情入库时将小红书 `#主题[话题]#` 格式抽取到独立 `tags` 字段，正文不再重复展示话题串。城市识别综合搜索词、标题、摘要、正文和话题，只在城市为空或“未分类”时自动回填，不覆盖用户修订。

## 3. 消息卡片契约

工具结果通过 `artifact.guides` SSE 事件实时发送，并加密持久化到 `conversation_message_artifacts`。历史对话重载后仍可重建同一组选择卡片。附件只保留内部候选 ID 和展示字段，不向浏览器发送 `xsec_token`。

同一次 Agent Run 可以为了覆盖不同人群、季节和行程风格执行多个搜索词，但不应把每次工具响应直接渲染成独立卡组。对话编排层在本轮结束时按内部 `candidate_id` 聚合，优先展示被多个不同查询命中的笔记，再按原搜索排名和首次出现顺序补齐。用户明确要求“N 篇”时最多返回 N 篇，未指定时默认 8 篇，系统上限 10 篇。完全相同的工具名和参数在本轮内直接复用首次结果，不重复消耗外部额度。前端读取旧消息时也会合并历史上已产生的多组附件，以保证只显示一组去重卡片。

展示前必须用当前用户的持久化记录回填状态，不相信搜索缓存中的旧状态。`ready` 项使用“本地已有”样式并排到候选末尾，仍允许勾选，此时语义是绕过详情缓存并检查来源更新。

批量导入采用 SSE 顺序事件：

- `import.started`
- `guide.started`
- `guide.completed` / `guide.failed`
- `import.completed`

这样既能在移动端显示真实进度，也能将单篇失败隔离，不阻断其他选中攻略。

## 4. 地点知识卡

统一卡片适用于 `attraction`、`restaurant`、`hotel`、`transport_hub` 和 `other`。卡片包含：

- 规范名称、城市、地址、经纬度；
- 简介、标签、来源引用和可信度；
- 营业时间、预约要求、项目列表、推荐必玩；
- 餐饮、美食、房型或服务项目；
- 价格清单及币种、适用时间和更新时间；
- 图片引用、最近核验时间、失效时间和版本号。

当前实现使用“用户 + Provider ID”生成不可逆身份键；没有 Provider ID 时使用规范化名称与城市。相同实体只更新，不新增副本。每次变更写入加密版本快照，允许后续做差异对比和恢复。

地图解析顺序为：有效地点卡坐标 → 外部工具缓存 → 高德查询 → 回写地点卡。行程节点因此不会在每次打开地图时重复消耗地理编码额度。

## 5. 多来源合并规则

字段更新按证据类型控制，不允许“最后写入者无条件覆盖”：

1. 用户明确编辑优先级最高；
2. 官方或地图结构化字段优先于社区文本；
3. 多篇攻略一致结论可提高置信度，但不能覆盖实时营业或票务来源；
4. 价格和营业时间必须带观察时间，过期后显示“待复核”；
5. 来源冲突时保留多个 Observation，由模型展示差异，不静默选择；
6. 模型只能生成更新提案，用户编辑和正式行程变更仍保留版本记录。

当前纵向切片已实现高德 POI 自动沉淀、坐标复用、用户卡片编辑，以及模型基于本轮证据调用 `place_knowledge_upsert` 合并 Claim。该工具要求提供证据来源、限制模型置信度上限，并写入版本快照；多来源冲突的专用对比 UI 在后续迭代接入同一合并契约。

整理多个地点时优先调用 `place_knowledge_batch_upsert`，单次最多 8 张；城市名会规范化“市”后缀，避免“青岛/青岛市”产生重复实体。Agent 每轮最多 16 次工具调用；达到工具轮次或总预算后，关闭工具进入最终汇总，不因某张卡失败丢失前面已成功的结果。成功卡片以 `artifact.places` 持久化，历史会话可点击重新查看。

## 6. 按需视觉分析

视觉模型与普通聊天模型分离。只有用户点击“识图”或显式导入图片资料时才执行：

```text
图片 URL/文件 -> 安全校验 -> 身份哈希 -> 已识别记录查询
  -> 命中：复用结果
  -> 未命中：视觉模型分类与抽取 -> 加密记录 -> 攻略整理/地点卡提案
```

记录键由用户、图片身份、模型名和提示词版本组成。升级提示词不会破坏旧结果，而会形成新的分析版本。当前远程图片使用 URL 身份去重；未来下载到本地对象存储后改用内容 SHA-256，可识别不同 URL 指向的相同图片。

视觉输出分两类：

- `guide_page`：提取可见文字、路线、地点、时间、预约、项目、价格、美食和注意事项；
- `place_photo`：只生成简短描述与语义文件名，不进行高成本全文整理。

视觉结果必须记录 `model_name`、`prompt_version`、`analysis_mode`、状态和分析时间。识别文本是二级证据，不能单独认定实时价格或营业状态。

## 7. 缓存与失效

| 数据 | 新鲜期 | 陈旧降级 | 更新方式 |
|---|---:|---:|---|
| 攻略搜索 | 6 小时 | 7 天 | 重新搜索 |
| 攻略详情 | 24 小时 | 7 天 | 用户刷新或导入重试 |
| 地图 POI | 7 天 | 7 天 | 地图/模型查询 |
| 地点卡坐标 | 30 天 | 不直接降级 | 过期后回查地图 |
| 图片分析 | 模型与提示词版本内长期有效 | 不适用 | 更换模型或提示词版本 |

缓存响应必须带采集时间和状态；`stale` 只能用于辅助建议，不能作为票务、营业或安全决策的唯一依据。

## 8. 模型使用流程

计划前的推荐流程为：

1. 与用户确认目的地、天数、人数、硬约束和攻略偏好；
2. 搜索候选攻略并用卡片让用户选择；
3. 下载所选详情，必要时由用户显式启动图片识别；
4. 从攻略库检索相关段落和地点 Claim；
5. 读取或补充地点卡，核验坐标和易变事实；
6. 生成候选计划并注明引用、冲突和待确认项；
7. 用户确认后才写入正式行程版本。

该流程支持模型主动提出“需要再搜索哪类攻略”，但搜索、视觉调用和正式数据变更分别受工具白名单、用量策略和用户确认控制。
