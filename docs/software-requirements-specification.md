## 1. 文档目的

本文定义智能旅游规划系统首版的功能范围、用户角色、业务规则、数据要求、外部接口、非功能要求、验收标准和版本边界，作为产品设计、技术设计、开发、测试和验收的共同基线。

本文中的要求使用以下优先级：

- **P0**：首版必须实现，缺失则不能完成核心闭环；
- **P1**：首版应实现，允许在不破坏核心闭环时顺延至 1.1；
- **P2**：已明确需要，但计划在后续版本实现；
- **Deferred**：暂不承诺实现，仅保留扩展接口或技术验证。

“系统必须”表示强制需求；“系统应”表示默认实现但允许经评审调整；“系统可以”表示可选能力。

## 2. 产品概述

### 2.1 产品定位

系统是一套面向个人、家庭和小范围用户的自托管智能旅游规划工具。系统通过大模型、地图、天气、攻略和用户订单资料，完成旅行需求整理、行程生成、路线优化、预算计算、合理性审计、行中调整、订单归档、实际消费记账和行后复盘。

系统不提供旅游商品销售，不介入支付，不代替用户登录第三方平台或自动下单。涉及机票、火车票、酒店、门票、餐厅套餐等商品时，系统提供估算、查询工具、外部链接和订单导入能力，最终购买由用户在第三方官方渠道完成。

### 2.2 核心价值

- 将自然语言需求转换为可编辑、可计算、可追踪的结构化旅行计划；
- 覆盖从出发地点到旅行结束返回的全过程路线；
- 根据人数、成员类型、房间、车辆和参与关系计算预算；
- 综合路线、时间、天气、营业、体力和预算检查计划合理性；
- 将分散攻略、订单、票据和消费统一归档；
- 允许用户通过对话和模块化界面持续修改，并确保模型始终读取最新状态；
- 支持家庭协作、权限、公开分享和完整修改历史；
- 在用户自己的 NAS 上运行，由用户掌控数据、模型 Key 和地图 Key。

### 2.3 产品目标

| ID | 目标 |
|---|---|
| OBJ-001 | 用户能够在手机端完成从创建需求到生成完整行程的全过程。 |
| OBJ-002 | 行程应覆盖出发、城际交通、市内活动、返程及到家路线。 |
| OBJ-003 | 用户能够通过对话、表单、卡片和地图修改同一份结构化行程。 |
| OBJ-004 | 系统能够输出计划预算、订单价格、实际消费及差异报告。 |
| OBJ-005 | 系统能够在不接入商业交易 API 的情况下完成主要使用闭环。 |
| OBJ-006 | 默认部署空闲内存低于 512 MB，正常任务峰值不超过 2 GB。 |
| OBJ-007 | 系统支持 AMD64 NAS 使用 Docker Compose 自主部署和升级。 |
| OBJ-008 | 用户能够配置 DeepSeek 或其他 OpenAI-compatible 模型。 |
| OBJ-009 | 所有关键事实、修改和 AI 操作均可追溯。 |

### 2.4 非目标

首版明确不包含：

- 自动购买或代订机票、火车票、酒店、门票和餐厅；
- 支付、收款、退款资金处理和佣金结算；
- 保存第三方平台账号密码，或在无用户明确授权的情况下自动登录 12306、OTA、小红书等；可选只读攻略 Provider 保存加密浏览器会话的边界见 FR-GUIDE-011；
- 验证码处理、抢票、占座和余票持续监控；
- 大规模采集第三方内容；
- 商家、供应商、分销和企业差旅采购后台；
- 原生 iOS/Android App；
- Kubernetes、高可用集群和大规模多租户；
- 默认运行本地大模型；
- 后台持续定位和完整轨迹记录。

## 3. 用户与角色

### 3.1 用户类型

| 角色 | 描述 |
|---|---|
| 系统管理员 | 初始化部署、管理系统配置、备份、更新、注册策略和资源限制。首个账号默认拥有该角色。 |
| 家庭管理员 | 创建家庭组、邀请成员、维护家庭默认配置、管理共享内容和执行恢复操作。 |
| 家庭成员 | 创建旅行、维护个人偏好、参与共享旅行、记账和导出。 |
| 访客 | 通过分享链接查看被授权内容，可按分享权限评论、复制或协作。 |
| 匿名访问者 | 仅可查看允许匿名访问的公开脱敏旅行，不可访问家庭和私有数据。 |

系统管理员与家庭管理员可以是同一账号，但权限模型必须分开表达。

| 查看家庭共享旅行 | 是 | 是 | 是 | 按分享权限 |
| 编辑旅行 | 按旅行配置 | 按旅行配置 | 按旅行配置 | 按分享配置 |
| 发布公开旅行 | 是 | 是 | 是 | 否 |

| 创建/恢复系统备份 | 是 | 经授权 | 否 | 否 |

### 3.3 家庭组

- 一个账号可以创建或加入家庭组；首版至少支持一个账号属于一个主要家庭组。
- 家庭组拥有默认模型、SMTP、旅行规则、成员档案和存储限额。
- 家庭组数据与成员私有数据在权限上必须分离。
- 家庭管理员不得默认查看成员私有旅行和私有聊天。

## 5. 总体业务流程

### 5.1 新旅行主流程

```text
创建旅行
  → 填写基础选项或直接对话
  → AI 结构化需求
  → 确认硬约束与关键缺项
  → 可选导入攻略和已有计划
  → 获取 POI、地图、天气和攻略事实
  → 生成节省/均衡/舒适三个方案
  → 计算路线、缓冲、预算和合理性
  → 用户选择并确认一个方案
  → 对话/卡片/地图持续编辑
  → 导入订单并替换相应估价
  → 出行中记录状态和局部调整
  → 记录实际消费
  → 输出行后复盘并更新用户记忆
```

### 5.2 状态事实原则

**FR-STATE-001（P0）** 数据库中的当前结构化行程状态必须是唯一事实来源，聊天历史不得作为行程当前状态的唯一依据。

**FR-STATE-002（P0）** 每次模型调用前，系统必须构造最新的行程快照、约束、偏好、锁定项和变更版本。

**FR-STATE-003（P0）** 用户通过表单、卡片、拖拽、地图或订单导入产生的修改必须落库，并对后续模型交互立即可见。

**FR-STATE-004（P0）** 当模型响应基于旧版本时，系统不得直接应用，必须提示冲突并重新计算或合并。

## 6. 功能需求

## 6.1 账号、认证与注册

**FR-AUTH-001（P0）** 系统首次启动必须引导创建系统管理员账号和离线恢复码。

**FR-AUTH-002（P0）** 首版必须支持用户名或邮箱加密码登录。

**FR-AUTH-003（P0）** 密码必须使用适合密码存储的强哈希算法保存，不得保存明文或可逆密码。

**FR-AUTH-004（P0）** 系统必须支持管理员直接创建账号和通过邀请链接/邀请码加入家庭组。

**FR-AUTH-005（P0）** 公开注册必须默认关闭，系统管理员可以在设置中启用。

**FR-AUTH-006（P1）** 配置 SMTP 后，系统应支持邮件找回密码；未配置 SMTP 时必须提供管理员辅助重置流程。

**FR-AUTH-007（P2）** 系统可以增加 TOTP 双因素认证，但首版不作为强制依赖。

**FR-AUTH-008（P0）** 所有登录失败、密码重置、恢复操作和权限变更必须写入审计日志。

验收：默认安装不能匿名进入家庭数据；关闭公开注册时无邀请用户不能注册；密码重置不能使已加密数据永久失效。

## 6.2 家庭组与成员档案

**FR-FAM-001（P0）** 用户必须能够创建家庭组、邀请成员、接受邀请和退出家庭组。

**FR-FAM-002（P0）** 家庭管理员必须能够直接创建成员账号、移除成员和设置角色。

**FR-FAM-003（P0）** 成员档案必须支持昵称、成员类型、年龄或出生日期、优惠资格、饮食、健康、行动能力和旅行偏好。

**FR-FAM-004（P0）** 系统不得要求保存身份证、护照等证件号码；优惠资格仅用于规划建议，购买时必须提示用户自行确认。

**FR-FAM-005（P0）** 成员本人和家庭管理员可以编辑成员资料；敏感字段必须支持本人限制可见范围。

**FR-FAM-006（P0）** 家庭成员档案可以在多次旅行中复用，每次旅行允许复制后覆盖而不修改原始档案。

**FR-FAM-007（P0）** 旅行参与者可以是家庭成员或临时同行人。

## 6.3 用户偏好与记忆

**FR-MEM-001（P0）** 系统必须支持家庭默认偏好、个人长期偏好和单次旅行偏好三个层级。

**FR-MEM-002（P0）** 偏好必须支持“必须满足、尽量满足、普通偏好、明确排除”四个等级。

**FR-MEM-003（P0）** 模型推断出的“必须满足”要求不得直接生效，必须经用户确认。

**FR-MEM-004（P0）** 用户必须能够查看、修改、禁用和删除模型记忆。

**FR-MEM-005（P0）** 旅行结束后，用户可以填写评价；模型可以提取潜在长期偏好，但写入记忆前必须向用户展示并确认。

**FR-MEM-006（P0）** 用户记忆至少包括常用出发地、预算档位、交通、酒店、餐饮、作息、节奏、不喜欢的类型和历史反馈。

## 6.4 创建旅行与需求收集

**FR-TRIP-001（P0）** 系统必须同时支持结构化表单创建和自然语言对话创建。

**FR-TRIP-002（P0）** 表单至少预设日期、出发地、目的地、人数、成员、预算和旅行风格。

**FR-TRIP-003（P0）** 用户未确定目的地时，系统必须能够根据出发地、日期、天数、预算、季节和兴趣推荐 3～5 个候选目的地。

**FR-TRIP-004（P0）** 目的地推荐必须说明推荐原因、预计交通、费用区间、适合人群、主要风险和来源。

**FR-TRIP-005（P0）** 系统默认支持最多 10 人、30 天、10 个城市；用户创建时可以输入实际规模。超过默认值时系统应提示性能影响而不是无提示失败。

**FR-TRIP-006（P0）** AI 只询问会显著影响路线、预算、安全或可行性的缺失信息；其他信息采用可见默认值。

**FR-TRIP-007（P0）** 系统必须在正式生成前展示结构化需求摘要、硬约束、软偏好和假设供用户确认。

**FR-TRIP-008（P0）** 每次旅行必须支持亲子、老人、情侣、朋友、独自、自驾、休闲、紧凑、美食、摄影等偏好预设；预设本质上是可编辑偏好集合。

## 6.5 方案生成

**FR-PLAN-001（P0）** 默认生成节省、均衡、舒适三个方案，用户可以改为只生成一个方案或指定数量。

**FR-PLAN-002（P0）** 每个方案必须包含整体摘要、每日行程、全过程路线、预算、风险、关键假设和来源。

**FR-PLAN-003（P0）** AI 可以推荐用户未指定的地点，但必须说明原因、来源、预计增加时间和费用。

**FR-PLAN-004（P0）** 方案必须遵循以下优化顺序：

1. 已确认必去、已预订和时间硬约束；
2. 交通衔接和可执行性；
3. 用户节奏、体力和同行人需求；
4. 减少折返和无效交通；
5. 控制预算；
6. 提高景点、餐饮和整体体验；
7. 保留自由时间。

**FR-PLAN-005（P0）** 每日计划应保留可替换候选，可覆盖天气、体力不足和预算不足场景；不要求默认生成三份完整备用日程。

**FR-PLAN-006（P0）** 系统必须支持导入 Markdown、PDF、截图或文字形式的已有计划，转换为模块化行程后进行优化。

## 6.6 行程模块化编辑

**FR-EDIT-001（P0）** 每个景点、餐厅、酒店、休息、集合点和交通段必须以独立模块保存和显示。

**FR-EDIT-002（P0）** 用户必须能够编辑地点、日期、开始/结束时间、停留时长、交通、价格、参与人、状态、备注、来源和锁定状态。

**FR-EDIT-003（P0）** 用户必须能够拖拽调整同一天地点顺序，并预览受影响的时间、路线和预算。

**FR-EDIT-004（P0）** 用户可以锁定城市、日期、地点、订单或交通段。全局优化不得修改锁定内容。

**FR-EDIT-005（P0）** AI 修改必须默认展示差异，用户确认后方可应用。

**FR-EDIT-006（P0）** 用户可选择局部修改或全局优化。局部修改只处理受影响范围；全局优化重新评估整趟旅行但保留锁定项。

**FR-EDIT-007（P0）** 系统必须支持撤销、重做、历史版本查看和版本恢复。

**FR-EDIT-008（P0）** 多人编辑必须使用版本冲突检测，不允许后保存者静默覆盖前一版本。

**FR-EDIT-009（P0）** 地点状态必须支持：必去、想去、AI 推荐、备选、不感兴趣、已锁定、已预订、已完成、已跳过。

## 6.7 地点卡片与地图联动

**FR-MAP-001（P0）** 页面内地图首版使用高德地图；百度用于可选 POI/路线补充和外部地图跳转。

**FR-MAP-002（P0）** 用户可以在设置中配置高德 Key 和可选百度 Key，未配置时系统仍能启动。

**FR-MAP-003（P0）** 地点卡片必须显示名称、类型、推荐原因、时间、时长、营业信息、费用、前后交通、地图标记、来源、可信状态和操作按钮。

**FR-MAP-004（P0）** 点击地图标记必须定位并高亮对应卡片；点击卡片必须高亮标记。

**FR-MAP-005（P0）** 地图必须支持按天显示路线、隐藏指定日期或类别、移动端全屏。

**FR-MAP-006（P0）** 用户拖动地图标记后，系统不得立即重写行程，必须展示影响范围并在确认后重算。首版保证基本拖动、坐标/POI 重新绑定和差异确认，P1 再优化移动端手势与批量操作体验。

**FR-MAP-007（P0）** 系统必须明确管理 WGS-84、GCJ-02 和 BD-09 坐标，不得直接混用。

**FR-MAP-008（P0）** 大型景区、机场和车站应优先使用入口或导航点，不只使用中心点。

**FR-MAP-009（P0）** 每个地点和路线应提供在高德打开的移动端链接；配置百度后可提供百度链接。

## 6.8 全过程路线与交通

**FR-ROUTE-001（P0）** 首版必须支持飞机、高铁/动车、普速火车、自驾、网约车/出租车、地铁/公交、步行和轮渡。

**FR-ROUTE-002（P0）** 一次旅行必须从用户出发地开始并以返回地结束，不能只生成目的地内的景点列表。

**FR-ROUTE-003（P0）** 出发地和返回地必须支持城市、车站/机场、具体地址和地图点。

**FR-ROUTE-004（P0）** 全过程至少包括：出发地至机场/车站、候车/值机、城际交通、到达至酒店、每日市内交通、返程至车站/机场、主干返程和到家。

**FR-ROUTE-005（P0）** 缓冲时间必须支持去机场/车站、值机安检、候车、换乘、找路、停车、排队、入住退房和行李寄存领取。

**FR-ROUTE-006（P0）** 缓冲时间有系统建议值，但用户可以全局或单项修改。

**FR-ROUTE-007（P0）** 多城市顺序支持用户指定、AI 建议和全局优化；用户可以锁定部分城市顺序。

**FR-ROUTE-008（P0）** 城际交通无法取得实时票价时，系统使用历史数据、用户预算或规则估算，并标记为待确认。

**FR-ROUTE-009（P0）** 系统可以提供联网查询工具或官方页面链接，用户回填或导入订单后更新价格。

**FR-ROUTE-010（P0）** 所有地图估价必须标注为估算，不得表示为实时可下单价格。

## 6.9 作息、节奏与体力

**FR-PACE-001（P0）** 系统必须提供休闲、均衡、紧凑和自定义节奏预设。

**FR-PACE-002（P0）** 用户可以设置但不强制填写起始时间、最晚返回、午休、每日最大活动、最大步行和休息频率。

**FR-PACE-003（P0）** 未设置作息时，系统只能将建议作为软偏好，不得伪装成用户约束。

**FR-PACE-004（P0）** 首日和末日应根据抵达、退房和返程时间使用不同排程规则。

**FR-PACE-005（P0）** 老人、儿童、行动不便、行李和天气因素必须进入体力合理性分析。

## 6.10 景点与游玩时长

**FR-POI-001（P0）** 景点候选必须综合地图、官方信息、攻略和用户偏好。

**FR-POI-002（P0）** 游玩时长必须综合官方建议、地图数据、多篇攻略和用户历史，优先输出范围而非虚假精确值。

**FR-POI-003（P0）** 系统必须区分营业、可能营业变化、暂停、关闭和未知状态。

**FR-POI-004（P0）** 需要预约或存在票种资格时，系统必须提示用户确认。

**FR-POI-005（P0）** 用户确认的营业时间、票价和时长应优先于旧的自动数据，但保留来源与修改历史。

## 6.11 餐饮规划

**FR-FOOD-001（P0）** 系统支持简单安排和详细安排两种模式。

**FR-FOOD-002（P0）** 详细模式支持早餐、午餐、晚餐、特色餐、主选和备选。

**FR-FOOD-003（P0）** 餐厅筛选必须考虑人均预算、菜系、距离、评分、营业时间、排队、预约、过敏、忌口、素食和清真等。

**FR-FOOD-004（P0）** 地图人均和攻略价格仅形成价格区间，不得虚构精确菜单总价。

**FR-FOOD-005（P0）** 用户可上传菜单、套餐或订单继续完善餐饮预算。

**FR-FOOD-006（P0）** 用餐计划必须包含合理用餐时段和从前一地点到餐厅的交通影响。

## 6.12 酒店规划

**FR-HOTEL-001（P0）** 系统必须支持用户导入已订酒店、推荐住宿区域和推荐具体酒店候选。

**FR-HOTEL-002（P0）** 酒店建议应优先考虑地点与整体路线，并结合预算、房型、停车、充电和成员需求。

**FR-HOTEL-003（P0）** 未接入实时价格时，只能展示价格区间和外部查询链接。

**FR-HOTEL-004（P0）** 用户最终确认酒店后，系统必须将其作为正式行程地点并重新计算路线。

**FR-HOTEL-005（P0）** 更换酒店时必须加入退房、寄存、领取、带行李移动和入住时间。

**FR-HOTEL-006（P0）** 携带大件行李时，应降低长距离步行和复杂公交换乘的推荐权重。

**FR-HOTEL-007（P0）** 房间预算必须支持家庭房、双床、多房间、房晚数和含早人数。

## 6.13 天气

**FR-WEA-001（P0）** 天气必须用于目的地建议、行前提示、室内外排序、穿衣雨具防晒建议、交通风险和行中备选。

**FR-WEA-002（P0）** 默认情况下天气只产生提示和备选建议，不得大幅改变成熟主计划。

**FR-WEA-003（P0）** 只有用户明确启用“按天气优先规划”或明确要求调整时，系统才可以主动移动主要景点和日期。

**FR-WEA-004（P0）** 系统应预设降雨、高低温、暴雨、台风、雷电、大风、暴雪、能见度和轮渡/景区风险规则，用户可调整阈值。

**FR-WEA-005（P0）** 天气导致的建议必须显示预测时间、数据更新时间和不确定性。

## 6.14 攻略资料库与外部来源

**FR-GUIDE-001（P0）** 系统必须支持导入链接、粘贴文本、图片、PDF 和 Markdown。

**FR-GUIDE-002（P0）** 用户可以配置允许模型自主查询的数据来源，也可以指定多篇攻略作为高权重参考。

**FR-GUIDE-003（P0）** 系统应支持自动搜索公开网页和官方文旅/景区信息，用户可关闭自动搜索。

**FR-GUIDE-004（P0）** 多来源分析必须考虑发布时间、新鲜度、共识、冲突、具体程度、疑似广告和能否被地图/官方信息验证。

**FR-GUIDE-005（P0）** 摘要必须保留原链接并区分事实、社区观点和模型推断。

**FR-GUIDE-006（P0）** 用户可以选择仅保存链接与摘要，或保存当前可见正文快照。

**FR-GUIDE-007（P0）** 默认保存链接、摘要、提取事实、哈希和获取时间，不默认永久复制完整图文。

**FR-GUIDE-008（P0）** 用户可以将来源设为信任、不信任或忽略，影响后续排序但不删除历史证据。

**FR-GUIDE-009（P0）** 首版小红书接入限于分享链接、用户粘贴内容或上传截图，不自动登录、不保存 Cookie、不调用非公开签名接口。

**FR-GUIDE-010（P1）** 系统应提供独立攻略资料库，支持按目的地、来源、旅行和标签检索。

**FR-GUIDE-011（P1/R）** 系统可以提供默认关闭的用户授权小红书只读查询 Provider。它只能保存用户主动扫码产生的加密浏览器会话，不保存账号密码，不提供发布或互动，不绕过验证码/风控，并且不可成为规划主链路依赖。完整规格见：[小红书旅游攻略查询工具规格与可行性研究](./xiaohongshu-guide-search-tool-spec-and-feasibility.md)。

## 6.15 大模型连接与编排

详细节点、状态、完整规划、局部修改、行中调整、质量门和恢复流程见：[旅游规划智能体详细流程规格](./agent-workflow-detailed-spec.md)。

**FR-LLM-001（P0）** 系统必须支持配置 OpenAI-compatible Base URL、API Key 和模型名，首选验证 DeepSeek API。

**FR-LLM-002（P0）** 家庭管理员可以配置默认模型；成员可以选择使用默认模型或配置个人模型。

**FR-LLM-003（P0）** 未配置任务专用模型时，所有任务必须回落到主模型。

**FR-LLM-004（P1）** 系统应预留主规划、低成本提取、审核、视觉、本地和备用模型角色。

**FR-LLM-005（P0）** 普通用户使用默认模型；高级设置允许手动选择模型。

**FR-LLM-006（P0）** 新模型连接必须测试普通对话、流式、JSON、Tool Calling、图片、用量和错误行为，并保存能力记录。

**FR-LLM-007（P0）** 模型不支持原生 Tool Calling 时，系统必须能够使用受 Schema 校验的两阶段工具请求或明确禁用工具功能。

**FR-LLM-008（P0）** 地图、天气和普通公开网页只读工具可以自动调用；登录态、文件、浏览器和高成本工具必须确认。

**FR-LLM-009（P0）** 工具循环必须有最大轮数、总时限和调用次数限制；地图、天气、云 OCR、网页抓取等外部数据工具还必须执行免费配额限制。DeepSeek 模型费用只统计，不因金额阈值阻断正常规划。

**FR-LLM-010（P0）** 模型不能直接写数据库。所有修改必须转换为经过 Schema、权限、版本和业务规则校验的命令。

**FR-LLM-011（P0）** 系统必须支持家庭规则、个人偏好、旅行临时规则和高级系统提示词模板。

**FR-LLM-012（P0）** 完整聊天应加密长期保存，用户可以导出、删除单次聊天，或在删除旅行时选择是否删除聊天。

**FR-LLM-013（P0）** 模型调用日志默认保存脱敏摘要、模型、时间、Token、费用、工具、耗时和错误；完整提示词保存策略由用户配置。

**FR-LLM-014（P0）** 系统必须按调用、行程、用户和月份统计模型 Token、缓存命中、峰谷时段和估算金额，并支持异常消耗提醒。DeepSeek 默认采用 `meter_only`，统计阈值不触发停止、排队或自动切换模型；管理员可以另行配置可选限制。

**FR-LLM-015（P0）** 模型价格表必须可配置，不能将外部模型价格永久硬编码。

**FR-LLM-016（Deferred）** 是否使用多模型分工必须通过质量、成本、延迟和稳定性对照实验决定，不作为首版成功的必要条件。

## 6.16 OCR、图片和文档识别

**FR-OCR-001（P0）** 首版采用本地 OCR 为主、视觉模型复核为辅。

**FR-OCR-002（P0）** 本地 OCR 结果必须展示给用户确认和修正，不得直接作为最终订单或消费记录。

**FR-OCR-003（P0）** 当用户认为结果不准确时，可以明确选择发送图片给已配置的视觉模型。

**FR-OCR-004（P0）** 地址、订单、票据、健康信息等发送云模型的权限必须按数据类型配置。

**FR-OCR-005（P0）** 系统必须支持文字、截图和 PDF 的订单信息识别。

**FR-OCR-006（P0）** 识别出的订单号、时间、地点、人员、价格、退改、座位、房型等字段必须逐项可编辑。

**FR-OCR-007（P0）** 原始文件、OCR 文本、用户修正和最终记录之间必须保留关联。

## 6.17 预算引擎

**FR-BUD-001（P0）** 用户可以设置总预算、人均预算、每日预算和分类预算，至少填写一种即可。

**FR-BUD-002（P0）** 系统可以根据旅行条件推荐预算范围和分类占比，用户可以手动优化。

**FR-BUD-003（P0）** 预算支持建议范围、目标值和硬性上限。

**FR-BUD-004（P0）** 超出预算时必须显示超支原因、金额、影响范围和节省方案。

**FR-BUD-005（P0）** 计价单位必须区分按人、按儿童、按老人、按车辆、按房晚、按订单、按天和实际消费。

**FR-BUD-006（P0）** 分摊必须支持平均、成员类型、指定参与人、指定付款人、家庭统一支付和朋友 AA。

**FR-BUD-007（P0）** 出租车必须按车辆数而非总人数简单相乘，并考虑行李和儿童座椅造成的容量变化。

**FR-BUD-008（P0）** 自驾预算必须支持能源费、过路费、停车、租车、保险和其他手工费用。

**FR-BUD-009（P0）** 酒店必须按房型、房间、房晚和入住人数计算。

**FR-BUD-010（P0）** 门票必须按票种与成员资格计算；资格未知时应使用上限估算并提示确认。

**FR-BUD-011（P0）** 餐饮人均数据只形成范围，用户确认菜单、套餐或订单后可以替换。

**FR-BUD-012（P0）** 每个价格必须标记为统计估算、路线估算、查询报价、已锁定价格或实际支付。

**FR-BUD-013（P0）** 价格必须保存来源、观察时间、有效期、币种、单位、包含项、排除项和置信度。

**FR-BUD-014（P0）** 支持人民币和外币，首版汇率由用户手工维护；实际支付汇率可单独记录。

## 6.18 订单归档

**FR-ORD-001（P0）** 用户可以通过文字、截图和 PDF 导入订单。

**FR-ORD-002（P0）** 系统必须尝试将订单匹配到对应的 TripItem 或 TripLeg，并展示匹配理由和置信度。

**FR-ORD-003（P0）** 订单确认后可以替换对应计划估价，但不得删除原估价。

**FR-ORD-004（P0）** 系统必须同时保存计划预算、订单价格和实际支付。

**FR-ORD-005（P0）** 订单必须支持状态、订单号、供应商、时间、地点、成员、座位/房型、价格、退改规则和附件。

**FR-ORD-006（P0）** 系统必须检查订单与行程时间、地点和参与人的冲突。

**FR-ORD-007（P0）** 取消、变更和退款必须形成新记录或状态事件，不得覆盖原始事实。

**FR-ORD-008（P0）** 保存订单前必须由用户确认识别和匹配结果。

## 6.19 实际消费与账单

**FR-EXP-001（P0）** 系统必须支持手工记账和从确认订单/票据生成消费记录。

**FR-EXP-002（P0）** 消费必须支持分类、金额、币种、时间、地点、付款人、参与人、计划关联、支付方式和备注。

**FR-EXP-003（P0）** 支持多人垫付、AA、家庭统一支付、部分退款、押金和预授权。

**FR-EXP-004（P0）** 系统不接入支付系统，支付方式仅用于记录。

**FR-EXP-005（P0）** 支持计划内和计划外消费，并在报告中分开统计。

**FR-EXP-006（P0）** 支持每日、分类、成员和整趟旅行统计，以及预算剩余和超支提醒。

**FR-EXP-007（P0）** 消费修正必须采用更正或冲销记录，保留原值、修正值、操作者、时间和原因。

**FR-EXP-008（P0）** 删除消费也必须保留不可变删除事件；彻底删除账号或恢复出厂时可以清除敏感内容。

## 6.20 行中模式

**FR-LIVE-001（P0）** 用户可以将旅行切换为行中模式，首页优先显示今天、下一地点、路线、订单、天气、预算和提醒。

**FR-LIVE-002（P0）** 行程项支持已出发、已到达、已完成、跳过、延迟和临时新增。

**FR-LIVE-003（P0）** 用户可以记录实际开始和结束时间。

**FR-LIVE-004（P0）** 系统支持“晚到、跳过、下雨、附近找餐厅、太累、预算不足”等自然语言局部重排。

**FR-LIVE-005（P0）** 默认只调整当天尚未完成的项目；用户可以选择调整当天、后续几天或整趟旅行。

**FR-LIVE-006（P0）** 已完成、较早已过去、已锁定和已预订项目默认不得修改。

**FR-LIVE-007（P0）** 重排必须展示修改前后时间、路线、预算和被影响的订单。

**FR-LIVE-008（P0）** 页面打开时可以请求当前定位；首版不得后台持续定位。

**FR-LIVE-009（P0）** 离线时必须能够查看已保存的行程、地址、订单、预算和清单；重新规划需要联网或本地模型能力。

## 6.21 通知与提醒

**FR-NOT-001（P0）** 系统必须提供站内提醒，并允许用户逐项开启或关闭。

**FR-NOT-002（P0）** 提醒至少包括出发、值机/候车、换乘、预约、入住退房、天气、预算、订单冲突、证件、行李和行前重新验证。

**FR-NOT-003（P1）** 管理员配置 SMTP 后，系统应支持邮件通知；SMTP 不是系统启动依赖。

**FR-NOT-004（P1）** 系统应支持导出 ICS，由用户导入苹果日历；首版不连接 iCloud 账号。

**FR-NOT-005（P2）** 浏览器 Push 可以作为后续可选能力。

## 6.22 行李与清单

**FR-LIST-001（P0）** 系统必须根据天气、天数、交通、成员和活动生成行李建议。

**FR-LIST-002（P0）** 支持家庭共用清单和个人清单。

**FR-LIST-003（P0）** 清单项支持勾选、数量、负责人、分类、备注和提醒。

**FR-LIST-004（P0）** AI 生成清单必须允许用户编辑，不能将建议表示为法规或强制要求。

## 6.23 安全与应急

**FR-SAFE-001（P0）** 旅行必须支持保存紧急联系人。

**FR-SAFE-002（P0）** 系统应提供医院、派出所等附近地点搜索。

**FR-SAFE-003（P0）** 应展示当地紧急电话、极端天气和景区安全提示。

**FR-SAFE-004（P2）** 海外版本预留保险、使领馆、护照和国际紧急信息。

## 6.24 旅行可见性、分享与公共旅行库

**FR-SHARE-001（P0）** 每次旅行必须支持私有、指定成员、家庭共享和公开四种可见性。

**FR-SHARE-002（P0）** 每次旅行可以独立配置谁能查看和编辑。

**FR-SHARE-003（P0）** 分享链接必须支持只读、评论、复制、协作编辑、密码、有效期和撤销。

**FR-SHARE-004（P0）** 公开旅行默认只允许查看和复制。

**FR-SHARE-005（P0）** 发布公开内容前必须生成脱敏预览并二次确认。

**FR-SHARE-006（P0）** 脱敏必须隐藏精确家庭地址、真实姓名、订单号、票据、付款信息、房间号、联系方式、健康信息和私密备注。

**FR-SHARE-007（P0）** 公开旅行保存独立脱敏副本，后续私有数据修改不得意外暴露。

**FR-SHARE-008（P1）** 公共旅行库支持目的地、天数、预算和风格搜索，支持收藏和复制。

**FR-SHARE-009（P1）** 公共内容支持作者撤回、管理员隐藏、访客举报、版本记录和匿名发布。

**FR-SHARE-010（P1）** 公开页默认禁止搜索引擎收录，发布者可以主动允许。

## 6.25 修改历史与审计

**FR-AUD-001（P0）** 所有业务数据变动必须写入审计事件，包括创建、修改、删除、恢复、分享、权限、消费、订单和 AI 应用。

**FR-AUD-002（P0）** 事件必须记录操作者、来源类型、时间、对象、版本、修改前后摘要和原因。

**FR-AUD-003（P0）** 必须区分用户手工修改、AI 建议应用、订单识别、系统自动更新和管理员恢复。

**FR-AUD-004（P0）** 行程必须保存不可变版本快照或可重建事件，支持恢复到历史版本。

**FR-AUD-005（P0）** 管理员访问成员私有数据的恢复操作必须记录并通知成员。

**FR-AUD-006（P0）** 账号彻底删除时，审计日志可以保留无敏感内容的删除事件，不得继续保留被要求删除的正文。

## 6.26 导出、导入与可移植性

**FR-IO-001（P0）** 系统必须支持旅行导出 Markdown、JSON、PDF 和 CSV。

**FR-IO-002（P0）** Markdown/PDF 应提供行前计划和行后复盘模板。

**FR-IO-003（P0）** 用户可以选择导出封面、成员注意事项、每日行程、交通、酒店、餐厅、预算、订单摘要、清单、应急、地图链接、攻略来源、实际消费和版本信息。

**FR-IO-004（P0）** PDF/Markdown 应包含可点击地图链接；PDF可以包含二维码。

**FR-IO-005（P0）** JSON 必须可被本系统重新导入，恢复结构化旅行而非仅恢复文本。

**FR-IO-006（P0）** CSV 至少支持预算、消费和分摊数据。

**FR-IO-007（P1）** 支持导出 ICS，每个行程项可形成日历事件，包含地点、提醒、地图链接和备注。

**FR-IO-008（P0）** 用户可以导出家庭全部数据的加密归档，并在新部署中恢复。

## 6.27 系统配置与简化管理页

**FR-ADM-001（P0）** 系统必须提供移动端可用的简化管理页。

**FR-ADM-002（P0）** 管理页必须支持模型、地图、SMTP、注册、存储、任务、日志、备份、更新和遥测设置。

**FR-ADM-003（P0）** 管理页应显示磁盘、数据库、附件、任务、模型/地图调用量、最近错误和备份状态。

**FR-ADM-004（P0）** 系统必须允许在没有模型、地图和 SMTP Key 时启动；相关功能显示未配置状态。

**FR-ADM-005（P0）** 用户必须能够测试模型和地图连接，并查看失败原因。

**FR-ADM-006（P0）** 匿名遥测和崩溃上报默认关闭，用户主动开启后方可发送。

## 6.28 备份、恢复与更新

**FR-BACK-001（P0）** 系统必须支持将备份写入管理员指定目录。

**FR-BACK-002（P0）** 支持每日备份、每周备份、重大更新前备份和手工备份。

**FR-BACK-003（P0）** 默认保留最近 7 份日备份和 4 份周备份，数量可配置。

**FR-BACK-004（P0）** 备份必须支持用户密码加密，默认不包含明文 API Key。

**FR-BACK-005（P0）** 系统必须支持从管理页或命令行验证、下载和恢复备份。

**FR-BACK-006（P0）** 管理页可以检查更新，但必须由用户确认安装。

**FR-BACK-007（P0）** 更新前必须自动备份，数据库迁移失败时必须停止升级并提供恢复路径。

**FR-BACK-008（P0）** 普通版本升级不得导致用户行程、聊天、订单、消费和附件丢失。

**FR-BACK-009（P0）** 首次初始化必须生成独立恢复码，并提示管理员离线保存。

## 7. 业务规则

### 7.1 数据优先级

发生冲突时采用以下默认优先级：

1. 用户当前明确确认的信息；
2. 已确认订单和实际消费；
3. 官方/地图实时或较新事实；
4. 用户指定高权重攻略；
5. 多攻略共识；
6. 系统规则估算；
7. 模型建议。

优先级高不表示覆盖历史。系统必须保留所有观察和变更，仅选择一个当前生效值。

### 7.2 事实状态

所有关键时间、价格、营业、路线和地点字段应具有以下状态之一：

- `verified`：由用户确认、订单或可靠工具验证；
- `estimated`：规则或外部估算；
- `suggested`：模型或攻略建议；
- `unknown`：没有可靠值；
- `stale`：值已超过有效期。

### 7.3 价格层次

- 地图 POI 人均、历史数据：统计估算；
- 路线过路费、公交、出租车：路线估算；
- 联网查询：查询报价；
- 已确认订单：订单价格；
- 支付/票据：实际消费。

不同层次不得互相覆盖删除。

### 7.4 删除与更正

- 普通业务删除采用软删除或墓碑事件；
- 订单、消费和退款使用变更事件或冲销；
- 用户可以执行隐私要求下的彻底删除；
- 彻底删除后，只能保留不含敏感正文的系统事件；
- 恢复出厂必须二次确认并提示最后备份。

## 8. 关键状态机

### 8.1 旅行状态

```text
draft → generating → proposed → confirmed → in_progress → completed → archived
                 ↘ failed        ↘ cancelled
```

- `draft`：需求编辑中；
- `generating`：AI/工具生成中；
- `proposed`：已有方案，待确认；
- `confirmed`：正式计划；
- `in_progress`：行中模式；
- `completed`：旅行结束，可复盘；
- `archived`：归档；
- `failed`：生成失败，可重试；
- `cancelled`：取消，订单与消费仍保留。

### 8.2 行程项状态

```text
candidate → planned → confirmed → booked → started → arrived → completed
       ↘ alternative     ↘ skipped / cancelled / delayed
```

“必去、想去、AI 推荐、不感兴趣、锁定”为标签/约束，不应与执行状态混为一个字段。

### 8.3 后台任务状态

```text
queued → running → waiting_user → succeeded
                   ↘ failed → retrying
queued/running → cancelled
```

任务必须保存阶段、进度、当前动作、已消耗资源和可重试性。

## 9. 数据需求

### 9.1 数据一致性

**DR-001** 所有实体使用稳定唯一 ID，不使用第三方 POI ID 作为内部主键。

**DR-002** 所有数据库时间以 UTC 保存，旅行和界面按用户/目的地时区显示；国内默认 `Asia/Shanghai`。

**DR-003** 金额使用十进制或最小货币单位存储，不允许使用二进制浮点直接结算。

**DR-004** 坐标必须同时保存坐标系和数据供应商。

**DR-005** 附件存文件卷，数据库保存哈希、MIME、大小、相对路径、加密信息和所属权限。

**DR-006** 价格、路线和外部内容必须保存获取时间和来源。

**DR-007** 行程版本应用乐观锁版本号，禁止静默覆盖。

### 9.2 数据保留

| 数据 | 默认保留 |
|---|---|
| 普通应用日志 | 30 天 |
| 模型调用元数据 | 90 天 |
| 完整聊天 | 加密长期保留，用户可删除 |
| 最终旅行文档 | 加密长期保留 |
| 审计事件 | 长期保留，隐私删除时脱敏 |
| OCR 临时文件 | 任务完成后尽快删除 |
| 原始订单/票据 | 加密保留，用户可删除 |
| 备份 | 7 日 + 4 周，管理员可配置 |

## 10. 外部接口要求

### 10.1 大模型

- 支持 OpenAI-compatible HTTP API；
- Base URL、Key、模型名均配置化；
- 支持流式和非流式；
- 接口差异由 Adapter 隔离；
- 所有调用有超时、重试、取消、预算和日志；
- Key 仅在服务端使用。

### 10.2 地图

- 高德为页面展示和主路线供应商；
- 百度为可选补充；
- 使用服务端 Adapter 统一 POI、路线和费用；
- 提供移动端 URI/HTTPS 跳转；
- 缓存稳定结果并对实时结果设置较短有效期。

### 10.3 天气

- 天气供应商可替换；
- 结果统一为当前、逐日、逐小时、预警和更新时间；
- 供应商失败时不阻断基本行程生成，只降低天气建议可信度。

### 10.4 网页和文件

- 普通公开网页优先轻量 HTTP 获取；
- 动态浏览器提取必须由用户授权并通过可选组件执行；
- URL 必须防 SSRF；
- 外部内容按不可信数据处理，不能成为系统指令。

### 10.5 邮件

- SMTP 由管理员统一配置；
- SMTP 未配置时不影响系统启动；
- 发送失败写入日志并保留站内提醒。

## 11. 非功能需求

## 11.1 性能与资源

**NFR-PERF-001（P0）** 默认部署在无活动任务时，服务端容器总空闲内存必须低于 512 MB。

**NFR-PERF-002（P0）** 正常规划、地图、OCR、PDF等受控任务期间，默认部署总峰值内存不得超过 2 GB。

**NFR-PERF-003（P0）** 若任务预计超过内存上限，系统必须排队、拒绝或降级，而不是继续启动并导致宿主机失稳。

**NFR-PERF-004（P0）** 首版按 AMD64 NAS、2 核 CPU、2 GB 最低可运行、4 GB 推荐配置设计，无 GPU 依赖。

**NFR-PERF-005（P0）** 普通页面操作在局域网目标响应 1 秒内，首屏目标 3 秒内。

**NFR-PERF-006（P0）** 地图/POI 查询目标 3～10 秒，简单 AI 修改 10～60 秒，完整多日规划 1～5 分钟。

**NFR-PERF-007（P0）** 支持最多 5 个家庭用户同时在线；每个家庭默认最多 1～2 个大型任务并发，其余排队。

**NFR-PERF-008（P0）** OCR、PDF和浏览器提取默认并发均为 1。

**NFR-PERF-009（P0）** 文件上传下载必须流式处理；列表、日志、消费和历史必须分页。

**NFR-PERF-010（P0）** 默认部署不得加载本地模型权重。Ollama等通过可选 Profile 或外部地址启用。

**NFR-PERF-011（P0）** 后端首版采用单 API Worker；重任务通过受控子进程或任务执行器完成并在任务结束后释放。

**NFR-PERF-012（P0）** 性能验收必须在目标 NAS 或等效 2 核/2 GB Linux 环境实测，不以开发机结果替代。

## 11.2 可用性与降级

**NFR-AVL-001** 未配置外部 API 时系统仍可登录、查看历史、手工编辑、记账、导入和导出。

**NFR-AVL-002** 模型失败时保存用户输入和任务阶段，允许重试或手工继续。

**NFR-AVL-003** 地图失败时允许使用缓存、直线距离或手工数据，不得虚构路线。

**NFR-AVL-004** OCR失败时保留原文件并允许手工录入。

**NFR-AVL-005** 后台任务必须可取消、可安全重试，并避免重复写入。

## 11.3 安全

**NFR-SEC-001** 默认只暴露 Web 端口，数据库、API内部端口、模型、OCR和任务执行器不得直接暴露公网。

**NFR-SEC-002** 公网部署由用户配置域名、HTTPS和反向代理；系统必须提供安全部署文档。

**NFR-SEC-003** 会话 Cookie 必须使用 HttpOnly、SameSite，并在 HTTPS 下使用 Secure。

**NFR-SEC-004** 必须防止 CSRF、XSS、SQL 注入、路径穿越、任意文件上传和 SSRF。

**NFR-SEC-005** 模型、地图、SMTP Key必须加密存储，不得写入普通日志或导出明文。

**NFR-SEC-006** 聊天、成员敏感资料、订单、票据、消费、文档和备份必须加密保存。

**NFR-SEC-007** 首次初始化生成恢复码；恢复码不得以明文长期存储在应用数据库。

**NFR-SEC-008** 上传限制默认：单图 20 MB、单 PDF 50 MB、单次 20 文件、家庭 20 GB，可配置。

**NFR-SEC-009** 浏览器提取组件必须隔离运行，不挂载 Docker Socket，不访问内网和本地文件。

**NFR-SEC-010** 模型和外部网页返回的内容必须经过 Schema 和权限检查，不能直接执行命令或写库。

## 11.4 隐私

**NFR-PRI-001** 系统必须按数据类型记录云模型授权，用户可随时撤销。

**NFR-PRI-002** 精确家庭地址允许替换为附近地点后再发送模型或公开分享。

**NFR-PRI-003** 管理员恢复成员私有内容必须有显式操作、审计和成员通知。

**NFR-PRI-004** 用户必须能够导出和彻底删除个人数据。

**NFR-PRI-005** 默认遥测关闭；开启后也不得发送聊天正文、地址、订单和票据。

## 11.5 兼容性与部署

**NFR-DEP-001** 提供 AMD64 Docker 镜像，使用 Docker Compose 一键启动。

**NFR-DEP-002** 安装允许联网拉取镜像；离线安装包不属于首版强制要求。

**NFR-DEP-003** 数据、附件和备份必须映射至持久化 Volume 或指定目录。

**NFR-DEP-004** 支持 iPhone/iPad Safari、Android Chrome、桌面 Chrome、Edge、Safari及 Firefox基本功能。

**NFR-DEP-005** 前端采用响应式 PWA，可以添加到手机主屏幕；首版不依赖原生 App。

**NFR-DEP-006** 数据模型预留多语言和多时区，首版简体中文。

## 11.6 易用性与无障碍

**NFR-UX-001** 手机首页以当前旅行、今天行程、下一地点、关键提醒和预算为核心，低频管理功能放入设置。

**NFR-UX-002** 旅行内部功能通过标签、底部菜单、抽屉和分层页面组织，不在单屏堆叠全部数据。

**NFR-UX-003** 支持深色模式、系统字体缩放、键盘操作和基本屏幕阅读器标签。

**NFR-UX-004** 关键破坏性操作必须二次确认并解释影响范围。

## 11.7 可维护性与开源

**NFR-MNT-001** 项目公开开源，并以个人/家庭小范围自托管为主要场景。

**NFR-MNT-002** 业务模块通过稳定接口解耦模型、地图、天气、OCR和存储供应商。

**NFR-MNT-003** 首版技术路线保持易开发和易贡献；Rust仅作为未来性能重构选项。

**NFR-MNT-004** 镜像和数据库 Schema必须有明确版本，更新不得依赖漂移的 `latest`。

**NFR-MNT-005** 开源许可证在发布前单独决定；当前候选为 Apache-2.0 或 AGPL-3.0。

## 12. 技术约束

首版默认技术基线：

```text
前端：React + TypeScript + Vite PWA
后端：Python + FastAPI + Pydantic
数据库：SQLite WAL
数据访问：SQLAlchemy + Alembic
文件：Docker Volume / 管理员指定目录
模型：OpenAI-compatible Adapter
地图：高德主用、百度可选
OCR：本地轻量 OCR + 可选视觉模型
部署：Docker Compose
```

约束：

- 默认不启动 Redis、PostgreSQL、Celery、LiteLLM、Langfuse、Ollama和长期浏览器服务；
- API 使用单 Worker；
- 重型 OCR、PDF和浏览器任务按需启动、执行完释放；
- PDF优先使用浏览器打印或轻量模板渲染；
- SQLite是首版唯一必需数据库，PostgreSQL只作为后续 Profile；
- 不因未来可能使用 Rust 而提前拆分复杂微服务。

## 14. 错误处理

| 场景 | 系统行为 |
|---|---|
| 模型超时 | 保留阶段，允许重试、切换模型或手工继续。 |
| 模型输出不符合 Schema | 自动修复一次；仍失败则展示可理解错误，不写库。 |
| 地图配额用尽 | 使用缓存/手工模式并提示日期和缺失影响。 |
| 天气不可用 | 继续生成主计划，标记天气未验证。 |
| 攻略无法读取 | 提示粘贴正文或上传截图。 |
| OCR不准确 | 用户修正或确认发送视觉模型。 |
| 版本冲突 | 展示双方差异，禁止静默覆盖。 |
| 存储不足 | 阻止新上传和备份，保留现有数据并提示清理。 |
| 邮件失败 | 保留站内通知和失败日志。 |
| 导出失败 | 保存任务错误，允许重新生成，不影响旅行本身。 |

## 15. 验收场景

### AC-001：家庭创建旅行

1. 管理员创建家庭组并邀请两名成员；
2. 创建 5 天、4 人、2 城市旅行；
3. 从表单填写日期、出发地、预算和节奏；
4. AI补充询问关键缺项；
5. 生成三个方案；
6. 成员可按权限查看并编辑；
7. 所有修改产生审计历史。

验收：模型再次对话时必须识别成员刚刚拖拽和锁定的地点。

### AC-002：全过程路线

用户从具体家庭地址出发，经火车站、高铁、目的地酒店、每日景点后返程到家。

验收：计划包含首末段、候车缓冲、城际段、酒店入住退房和全部市内 TripLeg；地图链接可点击。

### AC-003：多人预算

参与者为 2 成人、1 儿童、1 老人，使用 2 间房、1 辆网约车和不同门票类型。

验收：系统按正确计价单位计算总价和成员分摊，修改成员资格后只重算受影响项目。

### AC-004：订单导入

用户上传高铁订单截图，本地 OCR 识别后用户修正一个价格并确认。

验收：订单匹配到对应交通段，保留原估算和确认订单价，冲突时提示；所有识别与修正可追溯。

### AC-005：消费与退款

成员 A 垫付餐饮，4 人 AA；次日商户退款部分金额。

验收：账单保留原消费和退款事件，正确计算每人应付、已付和余额。

### AC-006：天气建议

目的地出现降雨和大风。

验收：默认只提示并给出室内候选，不自动移动已确认主景点；用户选择按天气调整后才生成差异方案。

### AC-007：行中局部重排

用户标记晚到 40 分钟并跳过一个景点。

验收：系统只调整当天未完成项目，保留已完成、锁定和订单项，应用前展示路线、时间和预算差异。

### AC-008：公开分享

用户将家庭旅行发布为公开链接。

验收：发布前显示脱敏预览；公开页不得出现家庭地址、姓名、订单、票据和付款信息；链接可撤销。

### AC-009：断开外部服务

移除所有模型和地图 Key后重启系统。

验收：系统正常启动，用户仍可查看、编辑、记账、导入和导出，AI/地图明确显示未配置。

### AC-010：备份恢复

创建加密备份，在全新部署中恢复。

验收：账号、家庭、行程、聊天、附件、订单、消费、审计和设置完整；API Key需按策略重新配置。

### AC-011：性能

在等效 AMD64 2核/2GB环境运行默认部署。

验收：空闲内存低于512MB；单个正常规划/OCR/PDF任务峰值不超过2GB；第2个重任务进入队列而非同时抢占资源。

| ID | 风险/验证项 | 处理 |

## 19. 已确定的设计基线与非阻塞验证项

- 项目许可证设计基线采用 Apache-2.0，并保留第三方 NOTICE/归属清单；正式公开发布前完成一次依赖许可证复核；
- TOTP/Passkey 保持 P2，不进入首版设计关键路径；
- 公开页默认禁止搜索引擎收录，发布者可在 P1 主动允许，按 FR-SHARE-010 实施；
- 首版使用默认主模型完成编排；多模型分工只有通过质量、成本、延迟和稳定性对照实验后才启用；
- 首版本地 OCR 基线为服务端轻量 PP-OCR 子进程，视觉模型仅在用户确认后复核；具体模型版本由脱敏样本 PoC 决定；
- PDF 基线为结构化数据渲染 HTML 模板后由受控 Chromium 打印；若目标 NAS 内存不达标，替换为轻量 PDF 渲染器而不改变导出契约；
- 高德 URI/HTTPS 跳转是 P0，专属地图导入为 P1 增强，等待账号能力实测；
- 苹果日历以 ICS 导出为 P1 基线，不承诺 iCloud 双向同步；
- 小红书用户授权浏览器查询为 P1/R，P0 仍使用链接、文本和截图导入。

## 20. 需求基线确认标准

本 SRS 可进入架构与开发阶段的条件：

- 产品负责人确认首版 P0 范围；

- 非阻塞验证事项均有负责人、验证方法、失败降级和目标版本。

## 附录 B：术语

- **硬约束**：用户明确确认、生成和优化不得违反的条件。
- **软偏好**：用于评分和排序，必要时可牺牲但需解释。
- **全过程路线**：从出发地到返回地，包含城际和市内全部主要交通段。
- **结构化行程快照**：某版本下Trip、日期、模块、路线、预算、约束和来源的完整状态。
- **局部重排**：只修改指定日期或受影响范围。
- **全局优化**：重新评估整趟旅行，但保留锁定、已完成和已预订项目。
- **价格观察**：在某个时间从某来源取得的估算、报价或实付记录。
- **脱敏副本**：从私有旅行生成、与私有数据隔离的公开版本。
- **模型记忆**：经用户确认的长期偏好摘要，不等同于完整聊天历史。
